# TIGERMARKIII 体验需求重梳理：从真实使用路径出发

版本：0.1  
日期：2026-05-23  
状态：替代前两版抽象方案的体验基准稿  

---

## 0. 这份文档解决什么

前两版文档的问题：先抽象、后套功能，导致看起来有结构，但没有回答用户实际怎么用、哪里痛、为什么要这样设计。

这份文档改为从真实使用路径出发：

```text
用户情境
→ 用户目标
→ 当前阻碍
→ 体验要求
→ 交互决策
→ 验收标准
```

不再先谈“工作区”“操作系统”“范式”这类大词。只有当具体体验推导需要时，才抽象。

## 1. 用户到底为什么打开这个扩展

用户打开 TIGERMARKIII，通常不是为了“管理书签”这个抽象目标，而是以下几种具体场景。

### 场景 A：我刚看到一个网页，怕以后找不到

用户状态：

- 正在浏览网页。
- 不想中断当前阅读。
- 只想快速保存。
- 最多愿意顺手选一下分类或标签。

体验要求：

- Popup 必须 3 秒内完成保存。
- 保存前不能强制用户整理。
- AI 分析可以建议，但不能成为保存阻碍。
- 保存后要告诉用户“保存到哪里了”，否则用户以后不知道从哪里找。

交互决策：

- Popup 是捕获工具，不是完整后台。
- Popup 只做当前页：保存、更新、快速分类/标签、可选 AI 理解。
- Popup 不放全库搜索、批量整理、同步、失效检测。

验收标准：

- 新用户第一次保存当前页，不需要理解分类/标签体系也能完成。
- 用户保存后能看到明确反馈：已保存、分类、标签、是否已生成摘要。

---

### 场景 B：我记得收藏过一个东西，现在要找

用户状态：

- 可能只记得关键词、网站、主题、分类位置中的一两个。
- 不想先决定“去分类页还是标签页”。
- 需要快速缩小范围。

当前阻碍：

- 搜索、分类、标签现在是分散入口。
- 分类在侧栏上方，标签只显示热门 20 个，无法系统浏览。
- 标签不是树，用户看不到语义层级。
- 搜索和分类/标签的联动不明显。

体验要求：

- 搜索、分类、标签、状态必须是同一个筛选系统。
- 用户输入关键词后，列表、分类树、标签树同时变化。
- 用户选分类后，标签树要变成该分类范围内的标签分布。
- 用户选标签后，分类树要显示在该标签条件下各分类还有多少结果。
- 当前范围必须用 chips 明确显示。

交互决策：

- 书签库左侧不叫“导航栏”，而叫“筛选器/范围面板”。
- 分类和标签并列分栏，不上下堆叠。
- 分类树和标签树独立滚动。
- 标签必须树化、可折叠。
- 搜索框同时搜索书签内容和 facet 名称，但不自动把搜索词转成标签。

验收标准：

- 用户可以在一个页面内完成：搜关键词 → 选分类 → 选标签 → 清除某个条件。
- 用户不用进入独立 `/tag` 或 `/category` 页面，也能完成同样目标。
- 零结果时，系统能告诉用户哪个条件可能导致范围过窄。

---

### 场景 C：我的收藏很多，我想浏览和筛选

用户状态：

- 不一定有明确关键词。
- 想通过分类、标签、状态逐步探索。
- 可能一边看结果，一边调整筛选。

当前阻碍：

- 分类和标签不是同等一等公民。
- 标签被压成“热门标签”，数量多时不可用。
- 侧栏滚动会导致分类和标签互相挤压。

体验要求：

- 分类和标签都是 facet tree。
- 两边都支持展开/折叠。
- 两边都支持搜索命中高亮。
- 两边都显示联动后的 count。
- 分类和标签应该独立滚动。

交互决策：

桌面版书签库左侧建议结构：

```text
Scope Bar
- 搜索框
- 当前筛选 chips

Status Strip
- 全部 / 未归档 / 已归档 / 失效 / 未检测

Facet Split
- Category Tree Pane
- Tag Tree Pane
```

分类树：

- 点击 chevron：展开/折叠。
- 点击名称：设为当前分类范围。
- checkbox：加入多分类筛选。
- 选父分类默认包含子分类。

标签树：

- 点击 chevron：展开/折叠。
- 点击名称或 checkbox：加入/移除标签筛选。
- 选父标签默认包含子标签。
- 多标签默认 AND，可切换 OR。

验收标准：

- 当分类树很长时，标签树仍然可见且可滚动。
- 当标签很多时，分类树仍然保持当前滚动位置。
- 用户能展开标签树找到低频标签，而不是只能依赖热门标签。

---

### 场景 D：我选中了一批书签，想批量处理

用户状态：

- 已经通过搜索/分类/标签缩小范围。
- 想对当前看到的一批书签做动作。
- 需要确定“我到底选了哪些”。

当前阻碍：

- 页面头部同时放全局批量按钮和选中项按钮。
- 用户容易分不清“处理全部、当前筛选、所选项”。

体验要求：

- 批量操作必须从明确范围开始。
- 选择态出现独立 Selection Bar。
- 全局批量任务不能和所选项任务混在一行。
- 多选不能依赖小 checkbox；卡片/行主体、键盘、框选都应该参与选择。

交互决策：

常态工具栏只放：

- 视图切换。
- 排序。
- 选择模式。

选择态工具栏显示：

- 已选 N 项。
- AI 归档所选。
- 补缩略图。
- 更新截图。
- 归档/恢复。
- 删除。
- 清除选择。

全局任务入口放到整理/维护区域，不放在书签库主标题右边。

选择方式必须按 `docs/selection-multiselect-ux-spec.md` 执行：

- 进入选择模式后，点击卡片/行主体即可选中或取消。
- checkbox 保留为状态提示和精确点击点，不作为唯一入口。
- 支持 Shift + 点击连续选择。
- 支持 `Arrow Up/Down/Left/Right` 移动焦点。
- 支持 `Shift + Arrow` 扩展选择。
- 支持 `Space` 切换当前焦点项。
- 支持 `Ctrl/Cmd + A` 选择当前 Scope 的全部结果。
- 网格视图支持拖拽框选。
- 当前可见项和当前筛选全部必须区分。

验收标准：

- 用户能清楚说出当前操作对象是“所选 N 项”，不是全部书签。
- 没有选中项时，不出现“删除所选”“归档所选”之类按钮。
- 用户不需要瞄准小 checkbox，也能高效选择多项。
- 键盘用户可以只用方向键、Shift、Space 完成连续多选。

### 场景 E：我想让 AI 帮我整理，但我怕它乱改

用户状态：

- 收藏已经乱了。
- 用户愿意让 AI 帮忙，但不完全信任。
- 最怕“标签越理越碎”“分类越分越细”“一键改坏”。

当前阻碍：

- AI 入口文案偏泛化：优化、助手、智能整理。
- 聊天和变更审批混在一起。
- 用户不一定知道 AI 会不会直接落库。

体验要求：

- AI 不能以“聊天”为主界面。
- AI 必须先给建议，再给变更预览。
- 大规模修改必须显示影响范围。
- 用户可以批准、跳过、修改建议。

交互决策：

AI 整理流程：

```text
选择范围
→ 选择整理目标
→ AI 生成建议
→ 建议按风险分组
→ 用户审阅
→ 应用变更
→ 结果记录
```

整理目标不能只叫“AI 优化”，要具体：

- 合并重复标签。
- 把扁平标签整理成层级。
- 找出未使用标签。
- 给未整理书签补分类和标签。
- 降低过细分类。

AI 输出必须结构化：

```text
建议 1：合并标签
影响：24 个书签，3 个标签
原因：同义词/大小写重复
风险：中
可撤销：部分可撤销
```

验收标准：

- 用户在点击应用前，能看到会改哪些标签、分类、书签。
- 用户能单独拒绝一条建议。
- AI 聊天不是唯一的操作记录。

---

### 场景 F：我想清理失效链接

用户状态：

- 不是为了浏览，而是为了维护收藏质量。
- 需要先知道哪些真的坏了。
- 删除前希望有分组和确认。

当前阻碍：

- 链接检测、失效链接、坟场是分散入口。
- 主页里有“检查失效链接”按钮，但健康维护没有统一入口。

体验要求：

- 健康维护应该是单独的体验路径。
- 链接检测是诊断。
- 失效链接处理是处置。
- URL 坟场是历史和恢复/追踪。

交互决策：

健康维护路径：

```text
健康维护首页
→ 查看上次检测状态
→ 开始检测
→ 结果按类型分组
→ 处理站点失效 / 页面失效 / 超时
→ 操作进入记录
```

失效处理动作：

- 打开确认。
- 修改 URL。
- 恢复为正常。
- 删除。
- 按域名批量删除站点失效。

验收标准：

- 用户能区分“检测”和“删除”不是同一步。
- 删除整个域名下的失效书签前，必须看到数量和域名。

---

### 场景 G：我想和 Chrome 书签同步或备份

用户状态：

- 操作风险高。
- 害怕覆盖或重复。
- 需要知道方向和冲突策略。

当前阻碍：

- 同步和备份埋在设置里。
- 设置页同时承载偏好项和高风险数据操作。

体验要求：

- 同步与备份应该从设置中拆出来。
- 每个同步操作必须先显示方向、范围、冲突策略。
- 清空数据不是设置项，而是危险操作。

交互决策：

同步与备份页面分三块：

1. Chrome 互通：导入、导出、双向同步。
2. 备份：导出 JSON、导入 JSON。
3. 危险区：清空数据、重置状态。

验收标准：

- 用户同步前能看见当前策略。
- 清空数据必须双确认，最好输入确认词。

## 2. 从这些场景推导出的核心设计

这一节不讲哲学，只做归纳和提取：从上面的具体场景里找重复出现的问题，然后提取成设计规则。

### 2.0 场景归纳表

| 具体场景 | 重复出现的问题 | 提取出的 UX 对象 | 提取出的规则 |
|---|---|---|---|
| 找收藏 | 用户记得的线索不固定，可能是词、分类、标签、网站 | `Scope` | 搜索、分类、标签、状态必须共同定义当前结果范围 |
| 浏览收藏 | 分类很多、标签很多，上下堆叠会互相挤压 | `Facet Pane` | 分类和标签必须分栏，且独立滚动 |
| 用标签缩小结果 | 标签不是扁平词，已有父子关系 | `Tag Tree` | 标签必须树化，可折叠，父标签默认包含子标签 |
| 组合筛选 | 用户需要知道为什么结果变少 | `Active Chips` | 当前筛选条件必须始终外显，可逐个移除 |
| 逐步探索 | 用户点下一个分类/标签前想知道是否有结果 | `Predictive Count` | count 必须随其他筛选条件联动，而不是显示全局静态数量 |
| 批量处理 | 用户怕误操作范围不清 | `Selection Scope` | 批量操作只在选择态出现，并显示已选数量 |
| AI 整理 | 用户怕 AI 直接乱改 | `Proposal` | AI 先给建议和影响摘要，再允许应用 |
| 失效清理 | 检测和删除是两个不同心理阶段 | `Diagnosis → Action` | 先诊断分类，再处理，不把检测按钮等同于删除入口 |
| 同步备份 | 用户怕覆盖、重复、清空 | `Risk Confirmation` | 同步/清空必须显示方向、策略、影响和确认 |

### 2.0.1 从场景中提取出的基础对象

这里的对象不是代码模型，而是 UX 中必须稳定存在的对象。

| UX 对象 | 从哪些场景归纳出来 | 含义 |
|---|---|---|
| `Scope` | 找收藏、浏览收藏、批量处理、AI 整理 | 用户当前要看的或要处理的一组书签 |
| `Facet` | 搜索、分类、标签、状态筛选 | 构造 Scope 的一个维度 |
| `Facet Pane` | 分类很长、标签很多 | 某个 facet 的独立浏览区域 |
| `Tree Node` | 分类、标签都有层级 | 可展开、可选择、可计数的节点 |
| `Active Chip` | 组合筛选、零结果 | 当前 Scope 的可见条件 |
| `Operation Scope` | 批量处理、AI 整理、同步 | 即将被操作影响的范围 |
| `Proposal` | AI 整理、标签治理、去重 | 系统建议但尚未落库的计划 |
| `Change Preview` | AI 整理、同步、删除 | 落库前的影响说明 |
| `Audit Result` | AI 执行、链接检测、同步 | 操作完成后的结果记录 |

### 2.0.2 从场景中提取出的动作

| 动作 | 不是指什么 | 实际含义 |
|---|---|---|
| 搜索 | 不是跳到搜索页 | 修改当前 Library Scope 的 query |
| 点分类 | 不是进入一个孤立分类页 | 修改 CategoryFacet |
| 点标签 | 不是进入一个孤立标签页 | 修改 TagFacet |
| 勾选多个标签 | 不是简单多选 UI | 构造 tag AND/OR 条件 |
| 全选当前列表 | 不是选择全库 | 选择当前 Scope 下的结果 |
| AI 整理 | 不是立即执行 | 生成 Proposal 和 Change Preview |
| 链接检测 | 不是处理失效链接 | 生成健康诊断结果 |
| 同步 | 不是设置项 | 高风险数据操作 |

### 2.0.3 从场景中提取出的交互规则

1. 用户在 Library 中的所有动作都应该能解释为“改变当前 Scope”或“对当前结果选择对象”。
2. 分类和标签在 Library 中是 facet，不是管理对象；管理对象的语义只在 Studio 中出现。
3. 一个条件是否生效，不能只藏在树节点 checkbox 里，必须同步显示在 chips 中。
4. count 的价值不是统计过去，而是预测下一步筛选后的结果规模。
5. 中高风险操作不能从按钮直接落库，必须先把 Operation Scope 显示出来。
6. AI 不能作为一个万能按钮出现，必须具体化为某种 Proposal。
7. 长任务结束不是体验终点，用户必须看到 Audit Result。

### 2.1 左侧 Sidebar 的真实职责

Sidebar 只在书签库中负责过滤。  
它的名字可以叫“筛选器”“范围”“探索器”，但不应该继续被理解为全局导航。

它的职责：

- 展示当前 Scope。
- 帮用户逐步收窄结果。
- 让分类和标签联动。
- 让用户理解为什么结果变少。

它不负责：

- 标签合并。
- 分类移动。
- AI 结构治理。
- 同步。
- 失效检测执行。

### 2.2 Category 和 Tag 必须联动

分类和标签不是两个孤立列表。

用户选分类后，标签必须变成“该分类范围内有哪些标签”。  
用户选标签后，分类必须显示“哪些分类下还有这个标签的书签”。  
用户输入搜索后，两棵树都必须基于搜索结果重新计数。

这才是体验上的“筛选”，否则只是静态目录。

### 2.3 Tag 必须树化

既然产品已经允许 tag 有 `parentId`，用户就会期待标签像分类一样有层级。

热门标签只能作为快捷区，不能替代完整标签树。

### 2.4 管理和筛选要分离

在 Library Sidebar 中，分类和标签是筛选工具。  
在 Studio 中，分类和标签才是被治理对象。

否则用户会在找资料时被“重命名、删除、合并”等管理操作干扰。

### 2.5 高风险操作从 Scope 开始

凡是会批量改数据的操作，都不能从按钮直接执行。

必须先显示：

- 当前范围。
- 影响数量。
- 会改哪些字段。
- 是否跳过某些项。
- 是否可撤销。

## 4. 书签库交互细则

### 4.1 搜索

用户输入搜索词：

- 结果列表实时变化。
- 分类树 count 联动变化。
- 标签树 count 联动变化。
- 匹配的分类/标签显示建议。

Enter 行为：

- 如果用户未选建议，则作为全文搜索。
- 如果用户选中建议，则添加对应 facet。

### 4.2 分类树

节点行为：

- chevron：展开/折叠。
- 名称：设为当前分类范围。
- checkbox：多选分类。
- 父分类默认包含子分类。

不建议：

- 单击名称同时展开和筛选。
- 在 Library 中暴露太多管理动作。

### 4.3 标签树

节点行为：

- chevron：展开/折叠。
- 名称/checkbox：添加或移除标签筛选。
- 父标签默认包含子标签。
- 多标签默认 AND。
- 提供“全部满足 / 任一满足”切换。

### 4.4 当前范围 chips

所有条件都必须显示为 chips：

```text
搜索 "react" ×
分类 技术/前端 ×
标签 性能 ×
标签 TypeScript ×
状态 未归档 ×
```

点击 x 只移除该条件。

### 4.5 零结果

零结果不只显示“没有匹配”。

应该显示：

```text
没有结果

当前条件：
- 搜索 react
- 分类 技术/前端
- 标签 性能 + TypeScript

建议：
- 移除 TypeScript
- 标签改为任一满足
- 清除分类
```

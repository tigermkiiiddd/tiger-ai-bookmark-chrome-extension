# TIGERMARKIII UX 范式重构：从书签列表到个人知识操作系统

版本：0.1  
日期：2026-05-23  
状态：重新抽象稿  
目的：推翻“页面 + 按钮 + 筛选器”的现有交互惯性，重新定义产品的 UX 底层模型。

---

## 0. 先说结论

TIGERMARKIII 不应该继续被设计成“一个带 AI 功能的书签列表后台”。

它应该被设计成：

> 一个围绕个人收藏资产的操作系统：用户给出意图，系统帮助确定范围、生成计划、预览影响、执行变更、留下可追踪记录。

这意味着交互核心不再是页面导航，而是：

```text
意图 Intent
→ 范围 Scope
→ 计划 Plan
→ 预览 Preview
→ 执行 Commit
→ 审计 Audit
→ 撤销 Undo
```

现在的产品范式是：

```text
用户进入某页面
→ 找按钮
→ 点功能
→ 功能直接执行或跳转
```

目标范式应该是：

```text
用户表达要完成的工作
→ 系统帮用户明确影响范围
→ 系统生成可审阅方案
→ 用户批准
→ 系统执行并记录
```

因此，重构重点不是“把按钮放哪”，而是把产品从“功能集合”重构为“意图驱动的工作流系统”。

---

## 1. 第一性原理：书签管理到底是什么

### 1.1 书签不是 URL

用户保存的不是 URL，而是：

- 一个未来可能要再访问的线索。
- 一个当时觉得有价值的知识片段。
- 一个任务、项目、兴趣、问题的外部引用。
- 一个未来检索时需要被重新理解的上下文。

因此，书签管理的本质不是 CRUD，而是降低未来再次使用信息的成本。

### 1.2 用户的真实焦虑

用户并不真正关心“我有多少标签”。用户关心：

- 我以后能不能找回来？
- 这个东西现在还有没有用？
- 我的收藏是不是乱到我不敢整理？
- AI 会不会越帮越乱？
- 我敢不敢让系统批量修改？
- 修改错了能不能回退？

所以 UX 必须围绕“信任”和“可恢复”设计，而不是围绕功能露出设计。

### 1.3 产品的核心价值

TIGERMARKIII 的价值不是“支持分类、标签、AI、截图、检测”。

这些只是能力。真正的价值是：

> 让用户在收藏越来越多时，仍然能低成本地保存、找到、理解、整理和维护。

如果功能越多，用户越不知道去哪、越不敢操作，那功能反而在破坏核心价值。

## 2. 领域对象抽象

现有 UI 把“书签、分类、标签、状态、AI 分析、同步”当成不同页面。  
更好的 UX 抽象是把它们看成同一套领域对象。

### 2.1 核心对象

| 对象 | 含义 | 用户怎么理解 |
|---|---|---|
| Bookmark | 被保存的信息线索 | 我收藏的一个东西 |
| Evidence | 这个书签为什么有价值的证据 | 摘要、截图、关键词、原网页信息 |
| Classification | 它属于哪里 | 分类路径、主题归属 |
| Tag | 它有什么特征 | 可交叉检索的语义标记 |
| Health | 它还能不能用 | 活跃、失效、重定向、未知 |
| Operation | 系统或用户做过什么 | 一次整理、一次检测、一次同步 |
| Proposal | 系统建议做什么 | AI 计划、合并建议、删除建议 |
| ChangeSet | 将要落库的一组变更 | 可预览、可批准、可撤销的修改包 |

### 2.2 一切高级功能都应落到 ChangeSet

这是重构的关键。

AI 归档、标签合并、分类移动、去重、同步冲突解决、失效链接批量删除，本质都是：

```text
对一组 Bookmark / Tag / Category 生成一组变更。
```

所以不应该每个功能各自设计一套确认方式。它们都应该进入同一个 ChangeSet UX：

1. 变更来源：用户 / AI / 同步 / 检测。
2. 影响对象：哪些书签、标签、分类。
3. 变更类型：新增、移动、删除、合并、更新状态。
4. 风险级别：低 / 中 / 高 / 极高。
5. 可撤销性：自动撤销 / 部分撤销 / 不可自动撤销。
6. 用户决策：应用 / 跳过 / 修改后应用 / 保存草案。

这会从根上统一所有复杂流程。

## 3. 用户意图抽象

不从页面出发，而从用户意图出发。所有交互都归为五个意图。

### 3.1 Capture：收进来

用户意图：

> 我现在看到一个网页，想以后还能找到。

UX 要求：

- 入口必须极短。
- 不要求用户立刻整理。
- AI 可以给建议，但不能阻塞保存。
- 保存后应告诉用户“以后从哪里找”。

适合界面：Popup。

### 3.2 Retrieve：找回来

用户意图：

> 我记得有这么个东西，想快点打开。

UX 要求：

- 搜索优先。
- 分类/标签是辅助透镜，不是主要任务。
- 结果页要强调可识别性：标题、域名、截图、摘要、标签。
- 不应把批量整理按钮放在最显眼位置干扰检索。

适合界面：Library Lens。

### 3.3 Understand：看明白

用户意图：

> 我想知道这个收藏是什么，为什么当时保存。

UX 要求：

- 详情应整合摘要、截图、标签、分类、原始 URL、状态。
- AI 分析是解释层，不只是字段。
- 用户可以要求“重新理解这个书签”。

适合界面：Bookmark Detail / Insight Panel。

### 3.4 Organize：理清楚

用户意图：

> 我的收藏结构乱了，我想让它变得可维护。

UX 要求：

- 必须先选范围。
- 必须先看计划。
- AI 是规划者，不是直接操作者。
- 结果应以 ChangeSet 呈现。
- 用户可以批量批准、局部修改、保存草案。

适合界面：Organize Studio。

### 3.5 Maintain：管得住

用户意图：

> 我想清理失效、重复、过期、同步冲突。

UX 要求：

- 问题按严重程度聚合。
- 先诊断，再处理。
- 批量删除必须按风险确认。
- 操作结果必须留记录。

适合界面：Maintenance Console。

## 4. 新交互范式：Lens + Operation

现有范式：页面等于功能。  
目标范式：页面只是某种 Lens，真正改变数据的是 Operation。

### 4.1 Lens：看数据的方式

Lens 是观察收藏资产的视角，不直接代表操作。

常见 Lens：

- 全部书签
- 最近收藏
- 未整理
- 已归档
- 失效
- 按分类
- 按标签
- 按域名
- 按项目/主题
- 搜索结果

Lens 的职责：

- 展示当前范围。
- 支持排序、筛选、选择。
- 进入详情。
- 将选中范围交给 Operation。

Lens 不应该承载大量业务按钮。

### 4.2 Operation：改变数据的操作

Operation 是对某个 Scope 执行的工作流。

常见 Operation：

- AI 理解
- AI 归档
- 合并标签
- 移动分类
- 检测链接
- 去重
- 补截图
- 同步
- 删除
- 导出

Operation 的通用结构：

```text
选择范围
→ 配置策略
→ 生成预览
→ 用户确认
→ 队列执行
→ 结果审计
```

任何 Operation 不能绕过这个结构，除非它是低风险单条操作。

---

## 5. Scope：范围是 UX 的中心

当前产品很多操作从按钮开始，这是错的。  
高风险操作应该从范围开始。

### 5.1 范围类型

| Scope | 例子 | 用户心智 |
|---|---|---|
| 当前书签 | 单条编辑、重新分析 | 只改这个 |
| 选中项 | 多选后批量操作 | 改我选的 |
| 当前 Lens | 当前筛选结果、当前分类 | 改我现在看到的范围 |
| 系统建议范围 | 未整理、失效、重复候选 | 系统帮我找了一批 |
| 全部 | 全库 AI 归档、全库检测 | 改全部，风险最高 |

### 5.2 范围确认模式

所有中高风险操作必须显示：

- 范围名称。
- 对象数量。
- 排除数量。
- 排除原因。
- 预计耗时。
- 可能影响的字段。
- 是否可撤销。

示例：

```text
即将整理：当前筛选结果
总计：823 个书签
将处理：517 个
跳过：306 个
- 已归档：220
- 失效链接：31
- 信息完整：55

将修改：分类、标签、摘要、归档状态
可撤销：可回滚本次变更集
```

## 6. Proposal / ChangeSet：AI 交互的核心抽象

### 6.1 AI 不是按钮，AI 是提案生成器

现在 UI 容易让用户感觉“点 AI，AI 就改”。  
目标 UX 应该是“AI 生成提案，用户批准变更”。

AI 的输出不应首先是聊天文本，而应是结构化 Proposal：

```text
Proposal
- 目标：减少重复标签
- 范围：全部标签
- 建议：
  - 合并 A/B/C 到 A
  - 移动 X 到 技术/AI
  - 删除 12 个未使用标签
- 预计影响：
  - 143 个书签
  - 26 个标签
- 风险：
  - 3 条高风险
  - 12 条中风险
  - 28 条低风险
```

聊天可以存在，但只是 Proposal 的解释和修订入口。

### 6.2 ChangeSet 是所有落库动作的唯一合法形式

高风险数据变更都应变成 ChangeSet：

```text
ChangeSet
- id
- createdAt
- source: user | ai | sync | link-check
- scope
- operations[]
- reversible
- status: draft | approved | running | applied | partially_applied | reverted
```

用户看到的不是“AI 正在整理”，而是：

> AI 生成了 42 条建议，预计影响 315 个书签。请审阅后应用。

### 6.3 ChangeSet 视图

ChangeSet 应有三个层级：

1. 总览：会发生什么。
2. 分组：按风险和类型分组。
3. 详情：每条具体变更。

示例：

```text
本次变更计划

低风险 18
- 重命名大小写不一致标签
- 补充空摘要

中风险 9
- 移动分类
- 合并同义标签

高风险 3
- 删除未使用标签
- 合并大量书签引用的标签
```

## 7. 新的产品结构不是“页面”，而是“四个空间”

### 7.1 Capture Space：捕获空间

位置：Popup。  
功能：快速保存当前页。

原则：

- 默认保存成功比整理完美更重要。
- AI 建议可以异步补充。
- 保存完成后告诉用户它在哪里。

核心路径：

```text
打开 Popup
→ 当前页识别
→ 显示已收藏 / 未收藏
→ 保存或更新
→ 可选 AI 理解
→ 结束
```

### 7.2 Library Space：检索空间

位置：主页面。  
功能：找、看、打开、轻量编辑。

它不是“所有功能的首页”，而是收藏资产的观察台。

核心元素：

- 全局搜索。
- Lens 切换。
- 结果列表。
- 详情面板。
- 选择态操作。

Library 的默认操作不是“整理”，而是“打开”和“理解”。

### 7.3 Studio Space：整理空间

位置：整理工作台。  
功能：执行有计划的结构调整。

Studio 的核心不是页面 tab，而是 Operation 流程：

```text
我想整理什么？
→ 整理哪些对象？
→ 系统建议怎么整理？
→ 我批准哪些？
→ 系统执行并记录
```

包含：

- AI 归档。
- 标签/分类治理。
- 去重。
- 批量截图。

这些都应共享同一套范围确认、队列执行、结果审计组件。

### 7.4 Console Space：维护空间

位置：健康维护 / 同步与备份。  
功能：诊断系统状态和处理风险。

Console 的核心不是浏览，而是：

- 检测。
- 告警。
- 冲突。
- 恢复。
- 备份。

这里的 UX 要更像运维控制台：清楚、谨慎、可追踪。

## 8. 重新定义导航

### 8.1 导航不按数据类型分

不要按“分类、标签、失效链接、设置”平铺。  
这会让用户以为每个名词都是一个功能岛。

应按用户意图区分：

```text
收进来：Popup
找回来：Library
理清楚：Studio
管得住：Console
配置它：Settings
```

### 8.2 分类和标签不是主导航

分类和标签是 Lens，不是顶层页面。

原因：

- 用户不是为了“进入标签页面”而来。
- 用户是为了“用标签缩小范围”或“治理标签结构”。
- 同一个标签既可以作为检索透镜，也可以作为治理对象。

所以：

- 在 Library 中，标签/分类是筛选 Lens。
- 在 Studio 中，标签/分类是治理对象。

这两个语义必须分开。

### 8.3 Sidebar 不是全局导航，而是上下文工具

上一条还不够具体。Sidebar 必须按空间改变职责：

- 在 Library 中，Sidebar 是 Facet Explorer，负责构造当前书签范围。
- 在 Studio 中，Sidebar 是 Operation Navigator，只显示任务导航和当前 Scope 摘要，不继续承担全局书签过滤。
- 在 Console 中，Sidebar 是 Issue Navigator，负责问题类型、严重度、检测批次等维护维度。
- 在 Settings 中，Sidebar 只是设置章节目录，或直接取消。

Library Sidebar 的具体规格见：

`docs/sidebar-faceted-filter-ux-spec.md`

核心要求：

- 搜索、分类、标签、状态共同构造 `LibraryScope`。
- 分类和标签是并列的 facet tree，不是上下堆叠的列表。
- 分类树和标签树必须分栏独立滚动。
- 标签必须支持树结构、展开/折叠、父标签包含子标签。
- 分类和标签的数量必须是联动预测计数，而不是静态总数。
- 当前筛选必须以 chips 明确展示，用户不应靠找 checkbox 才知道当前范围。

## 9. 重新定义主页

现有主页是功能按钮集合。  
目标主页应该是 Library Space，而不是 Dashboard。

### 9.1 Library 首页应该回答

- 我有多少书签？
- 最近保存了什么？
- 我现在能快速搜索什么？
- 哪些收藏需要注意？
- 我当前看到的是哪个范围？

### 9.2 Library 首页不应该回答

- 我要不要去重？
- 我要不要全库 AI 归档？
- 我要不要检查坏链接？
- 我要不要打开标签治理？

这些属于 Studio / Console 的提示，可以作为轻量提醒出现，但不能成为主页主操作。

示例：

```text
书签库
搜索...

Lens:
全部 / 最近 / 未整理 / 已归档 / 失效 / 重复候选

Content:
书签结果

低调提醒:
有 36 个书签可能失效 · 去健康维护
有 120 个未整理书签 · 去整理工作台
```

## 10. 重新定义 AI

### 10.1 两种 AI

必须区分：

| AI 类型 | 场景 | 输出 | 风险 |
|---|---|---|---|
| Understanding AI | 单页理解、摘要、标签建议 | Evidence / Classification | 低 |
| Governance AI | 全局整理、合并、移动、删除 | Proposal / ChangeSet | 中高 |

现在产品容易把两者混在一起，所以用户会困惑：

- AI 到底是在分析这个网页？
- 还是要改我的整个书签库？
- 它会不会直接落库？

### 10.2 AI 入口文案

不使用泛化文案：

- AI 整理
- 智能优化
- AI 标签助手

改为意图明确：

- 理解当前页
- 为这些书签补充分类和标签
- 生成标签合并建议
- 查找重复结构
- 预览本次变更

### 10.3 AI 聊天的位置

聊天不是主界面。  
聊天是对 Proposal 的自然语言编辑器。

正确结构：

```text
左侧：结构视图 / 列表 / 标签云
中间：Proposal / ChangeSet
右侧：AI 对话，用来解释和修改 Proposal
```

而不是：

```text
左侧标签云
右侧聊天
聊天里混着工具调用和审批
```

## 11. 操作状态机

所有长流程统一状态机。

```text
draft
→ ready
→ running
→ paused
→ completed
→ audited

异常：
running → failed
running → cancelled
completed → reverted
```

### 11.1 draft

用户或 AI 正在形成计划。  
不能落库。

### 11.2 ready

计划完整，范围明确，用户可以开始。

### 11.3 running

队列执行中。  
必须显示进度和当前项。

### 11.4 paused

用户主动暂停。  
应显示当前暂停点。

### 11.5 completed

执行结束。  
不等于用户已经理解结果。

### 11.6 audited

用户看过结果或系统生成了结果摘要。  
这才是完整闭环。

## 12. 交互语法

TIGERMARKIII 应形成统一交互语法：

```text
在 [范围] 上，用 [策略] 做 [操作]，先给我看 [影响]，我确认后再执行。
```

例子：

```text
在 当前筛选结果 上，用 保守策略 做 AI 归档，
先给我看会修改哪些分类和标签，我确认后再执行。
```

```text
在 全部标签 上，用 合并同义词策略 做 标签治理，
先给我看高风险合并项，我逐条确认。
```

```text
在 30 天未检测书签 上，做 链接检测，
自动跳过最近检测过的，结束后按站点失效和页面失效分组。
```

这个语法应该贯彻 UI、AI prompt、MCP tool、内部代码模型。

## 13. 关键 UX 决策

### 13.1 删除“功能按钮首页”

主页不再承担功能集散地。  
功能入口归入 Studio / Console。

### 13.2 删除“标签页/分类页”的独立心智

标签页和分类页不应是孤岛。  
它们是 Library 的 Lens 状态：

```text
/library?lens=category&id=xxx
/library?lens=tag&id=xxx
```

### 13.3 删除“AI 聊天即工作台”的范式

AI 聊天不能成为结构治理的主体界面。  
主体必须是 Proposal / ChangeSet。

### 13.4 删除“alert/confirm 即反馈”的范式

浏览器 alert/confirm 会打断工作流，且无法承载影响摘要。  
高风险操作必须使用产品内确认组件。

### 13.5 删除“设置页塞所有系统操作”的范式

同步、备份、清空数据、恢复数据是 Console 操作，不是普通偏好设置。

## 16. 最小可行重构路径

不要先大改视觉。先改交互模型。

### Step 1：建立 Scope 和 Operation 概念

新增统一的操作启动模型：

```ts
OperationDraft {
  type
  scope
  strategy
}
```

所有批量入口都先生成 OperationDraft，而不是直接跳页面或执行。

### Step 2：把 AI 归档改成标准 Operation

AI 归档先显示：

- 范围
- 将处理数量
- 跳过数量
- 修改字段
- 是否可撤销

再开始执行。

### Step 3：把标签工作台改成 Proposal 优先

当前 Agent 视图从“聊天 + 标签云”改为：

```text
标签结构视图
Proposal 列表
AI 解释/修订面板
```

### Step 4：把主页还给 Library

移除主页上的重型任务按钮。  
保留搜索、Lens、视图、排序、选择态批量动作。

### Step 5：引入 Console

把链接检测、失效链接、坟场、同步备份统一归入 Console。

## 17. 判断设计是否正确的标准

如果重构后用户能说出下面这句话，就对了：

> 我平时在书签库找东西；要整理时进整理工作台；要处理坏链接和同步备份时进控制台。AI 会先给我方案，不会偷偷乱改。

如果用户仍然说：

> 我不知道这个按钮会改什么，也不知道应该去哪整理标签。

那就是失败。

## 18. 与上一版 UI 文档的关系

上一版 `interaction-layout-redesign.md` 可以保留作为页面布局参考，但它不应作为顶层设计依据。

顶层设计应以本文为准：

1. 先定义 Intent。
2. 再定义 Scope。
3. 再定义 Operation。
4. 再定义 Proposal / ChangeSet。
5. 最后才定义页面和布局。

换句话说：

```text
UX 不是“页面怎么摆”。
UX 是“用户如何安全、可理解、可恢复地完成真实任务”。
```
